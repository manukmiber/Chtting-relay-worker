1. Base URL and endpoints

The relay speaks the OpenAI HTTP API. Any OpenAI-compatible SDK, client or agent framework works unchanged — point its base_url at the relay and give it a client key.

base_url = https://<your-relay-host>/v1

Every path exists with and without the /v1 prefix. Some clients append /v1 themselves, others are handed a base URL that already ends in it. Both spellings hit the same handler, so neither configuration is wrong.

GET /health is the only endpoint that never needs a key, and the only one safe to poll from a monitor:

{"status":"ok","service":"chtting-relay","version":"2.0.0",
 "models":3,"backends":1,"uptime_s":81422,"in_flight":2}

Tunnel addresses move. If the relay is published through a quick Cloudflare tunnel, the hostname changes every time the tunnel restarts. Ask the operator for a named tunnel hostname before hard-coding a URL anywhere.

2. Authentication

Every endpoint except /health and CORS preflight takes a client key as a bearer token:

Authorization: Bearer Kunci-Zeiko-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX

A key sent bare — the value with no Bearer scheme in front of it — is also accepted, because some clients send it that way.

The model listing needs a key too. GET /v1/models is authenticated on this relay. A client that fetches the model list before it has been given credentials will get 401, not an empty list. Configure the key first, then discover models.

The two kinds of client key

A key has a kind, and the kind decides one thing: whose behalf this request is on. Everything else follows from that. Your operator will tell you which kind you hold.

companyprivate
Who is behind the keymany end usersone holder
Identity sent upstreamthe one you send (see section 4)the key's own identity
If you send userusedignored
Usage broken down byend userkey
Output speed capmay applynever applies

A company key is a reseller key: each call carries its own end user, and that id is what isolates one customer's prompt cache from another's. A private key is one person, so anything you put in user is ignored and the key's own identity (a stable fingerprint, not the key itself) is used instead.

3. Making a request

POST /v1/chat/completions takes the ordinary OpenAI request body. Two fields are required: model and messages.

curl -N https://<your-relay-host>/v1/chat/completions \
  -H "Authorization: Bearer Kunci-Zeiko-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: customer-42" \
  -d '{
    "model": "Wissangeni-512B-V1",
    "messages": [
      {"role": "system", "content": "You are a helpful assistant."},
      {"role": "user",   "content": "Hello!"}
    ],
    "stream": true,
    "temperature": 0.7,
    "max_tokens": 512,
    "user": "customer-42"
  }'

What the relay acts on, and what it forwards

Parameters the relay does not act on are forwarded to the backend untouched. Whether the second group has any effect therefore depends on the routed model, not on this relay.

max_tokens

stoprelayUp to four entries, as OpenAI. The relay may add one of its own within that limit.
user / user_idrelayThe prompt-cache isolation key. See section 4 — read it.
reasoning_effortrelaynone, minimal, low, medium, high, max. Selects the system prompt and can move the price. Also read from reasoning.effort, thinking.effort, extra_body.reasoning.effort, the on/off switches enable_thinking, reasoning.enabled, thinking.enabled, thinking.type: "disabled", and from a budget in thinking.budget_tokens, reasoning.max_tokens or thinking_budget.

Check supported_parameters before you rely on a parameter. Each model's entry in /v1/models lists exactly what it accepts, and that list is derived from the live configuration — a parameter an operator has configured the relay to drop disappears from it. Sending something that is not listed is not an error; it simply has no effect.

Requests to /v1/completions and /v1/embeddings

/v1/completions takes the legacy body and goes through the same routing, the same quotas and the same accounting as chat. /v1/embeddings takes model plus input (a string or an array of strings) and returns the provider's embedding response with one change: model in the response is rewritten back to the public id you asked for. There is no streaming and no reshaping on that path.

4. User ID and KV-cache isolation

Send a stable, opaque identifier for your end user on every request. This is the single most important thing to get right in an integration, and it is worth a section of its own.

Why: KV-cache isolation

The backends behind this relay cache the attention keys and values computed for a prompt prefix (the KV cache) and key that cache per user. The user id you send is what partitions it.

  • Correctness. Without an id, every caller behind one API key lands in the same cache partition. One tenant's prompt prefix becomes reusable by another tenant's request — exactly the leak the id exists to prevent.
  • Cost and latency. A cache hit is billed at the cache-read rate, which is a fraction of the fresh-input rate, and it removes most of the time-to-first-token on a long system prompt. A user id that changes between requests destroys every hit; a stable one keeps them.

Where to put it

Two places, and the body wins over the headers:

WhereField / headerPrecedence
Request bodyuser1 — checked first
Request bodyuser_id2 — used when user is absent or blank
HeaderX-User-Id3
HeaderX-User4
HeaderX-OpenAI-User5
HeaderX-KV-User6

The first of those that carries a non-empty value (after trimming whitespace) wins. Using the body field user is recommended: every OpenAI SDK already exposes it, so nothing custom is needed.

// OpenAI SDK, any language — the standard field is enough
{
  "model": "Wissangeni-512B-V1",
  "messages": [ ... ],
  "user": "tenant-42:user-9f3c1ab7"
}
# Or as a header, for clients that cannot add a body field
X-User-Id: tenant-42:user-9f3c1ab7

What we do with it

Whichever way it arrives, the same string is recorded on the request row, written to the log line, and forwarded to the backend in three places at once so that no backend spelling is missed:

Sent upstream asWhy
Header X-User-IdThe header name is configurable per backend; x-user-id is the default. Header values must be ASCII, so an id that is not ASCII is simply not sent as a header — the body fields below still carry it.
Body userOpenAI's spelling.
Body user_idThe second spelling, because backends disagree on which one they read. A backend reading only the one we did not send would pool every caller behind this relay into a single cache — which is the whole failure mode.

If you send nothing, that is allowed: the request is recorded with an empty user, and user and user_id are removed from the body before it goes upstream rather than being left at whatever unusable value arrived. Cache isolation is then whatever the backend does by default, which is to say: none of your own.

Rules for choosing the value

  • Stable. The same end user must get the same string on every request, across sessions and across process restarts. This is what makes the cache hit.
  • Unique per end user. Two different people must never share one id, or they share a cache partition.
  • Opaque. Send a pseudonymous identifier — a hash, a UUID, an internal account id. Do not send an email address, a phone number, a username or a real name. The id travels to a third-party backend and lands in its logs.
  • Short. The recorded value is truncated at 120 characters. Keep it well under that.
  • ASCII. Non-ASCII ids still work but cannot ride in the header, so the backend only sees them in the body.

Private keys: if you hold a private key, none of the above applies — whatever you send is ignored, and the key's own stable fingerprint is what travels upstream and what your usage is filed under. You cannot land in another holder's cache partition, and nobody can land in yours.

Cache retention is the backend's to state, not this relay's. Nothing about your prompt is stored here beyond a truncated preview on the operator's own Requests screen. If you need a retention figure in writing, ask the operator to obtain it from the upstream provider.

5. The response we send back

Nothing the backend says about itself reaches you. Every reply is rebuilt from an envelope the relay owns — its own id, its own timestamp, its own model name — and only a named handful of fields are copied across. The backend's model name, host, request id and error wording never appear in any response.

The usage block — the fields to bill from

prompt_tokens is counted by this relay's own tokenizer over your own messages, measured before anything was injected. A system prompt the relay adds on your behalf is not charged to you, so the figure matches what you actually sent.

FieldTypeMeaning
usage.prompt_tokensintegerInput tokens, over your own messages only.
usage.completion_tokensintegerOutput tokens, reasoning tokens included.
usage.total_tokensintegerThe two above, added.
usage.prompt_tokens_details.cached_tokensintegerThe cache-hit portion of the input. Never larger than prompt_tokens. Absent when zero — this is your signal that user-id isolation is working.
usage.completion_tokens_details.reasoning_tokensintegerThe reasoning portion of the output. Absent when zero.

usage.costnumberThe same number under OpenRouter's spelling. It is never a second, different price.

Nine decimal places is deliberate. A short request at a tenth of a dollar per million tokens comes to a few millionths of a cent; rounding to six places would report every small request as free. Parse it as a decimal, not as a float, if you are reconciling invoices.

6. Streaming (SSE)

Send "stream": true and the response is text/event-stream: one data: frame per chunk, then a final frame carrying usage, then [DONE].

Response headers on a stream

content-type:      text/event-stream; charset=utf-8
cache-control:     no-cache, no-transform
connection:        keep-alive
x-accel-buffering: no
x-relay-request-id: 32dadfde-f3dd-4ad8-acc5-387b72415f46

The frame sequence

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1","provider":"zeikoai",
       "choices":[{"index":0,"delta":{"role":"assistant"},
                   "finish_reason":null,"native_finish_reason":null}]}

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1","provider":"zeikoai",
       "choices":[{"index":0,"delta":{"content":"Hel"},
                   "finish_reason":null,"native_finish_reason":null}]}

: Zeiko is still here, Just be patience

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1","provider":"zeikoai",
       "choices":[{"index":0,"delta":{"content":"lo!"},
                   "finish_reason":"stop","native_finish_reason":"stop"}]}

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1","provider":"zeikoai",
       "choices":[],
       "usage":{"prompt_tokens":18,"completion_tokens":256,"total_tokens":274,
                "usage":0.010293,"cost":0.010293}}

data: [DONE]

(Frames are shown wrapped for print. On the wire each data: payload is a single line, and every frame is terminated by a blank line.)

What a client must handle

FrameRule
First frameCarries delta.role: "assistant" and usually no content. Do not assume it has text.
Content framesdelta.content is a string fragment. Concatenate in arrival order. A reasoning trace, when the route passes one through, arrives as delta.reasoning_content or delta.reasoning alongside — or folded into content between tags, depending on the route's configuration.
Tool callsdelta.tool_calls arrives as partial fragments keyed by index, in the usual OpenAI way: accumulate function.arguments across frames before parsing.
Comment linesA line beginning with : is an SSE comment — a keep-alive, sent after roughly 15 seconds of backend silence (the operator can change the interval and the text, or switch it off). Discard it. A compliant SSE parser already does; a hand-rolled one that does line.startswith("data: ") is also fine. Never try to JSON-parse it. It exists to hold the connection open through tunnels and NATs, and it is the relay's own — the backend's keep-alives are parsed and dropped here, never forwarded.
Final usage frameHas an empty choices array and carries usage. It arrives whether or not you sent stream_options.include_usage. A client that assumes choices[0] exists on every frame will crash here — guard it.
Error frameIf the backend fails part-way through, a frame carrying {"error":{"message":…,"type":"upstream_error"}} is emitted before [DONE], so a stream that has already started never just ends in silence. The HTTP status stays 200: it was already sent.
data: [DONE]The terminator. Always last, and not JSON.

Guarantees and gotchas

  • id, created, model and provider are identical on every frame of one response.
  • Frames may be split across TCP reads. Buffer until a blank line before parsing, and accept both \n\n and \r\n\r\n as the separator.
  • Multi-byte characters are reassembled by the relay, so a UTF-8 character is never split across two frames' delta.content.
  • Output may be paced: a company key's stream can be held to a configured tokens-per-second ceiling, so a slow stream is not necessarily a slow model. Private keys are never paced.
  • Use curl -N, and turn off response buffering in your HTTP client. The relay sends x-accel-buffering: no so nginx and cloudflared do not buffer; an intermediary you control might still.
  • Set your client timeout above the backend timeout (default 10 minutes) — with keep-alives on, an idle-read timeout will not fire spuriously, but a total-request timeout can.
  • If you disconnect mid-stream the relay stops and records the request as cancelled. You are still accounted for what was generated up to that point.

7. Listing models: /v1/models and /models

Both paths return the identical document. /v1/models/{id} and /models/{id} return a single entry from it.

curl https://<your-relay-host>/v1/models \
  -H "Authorization: Bearer Kunci-Zeiko-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX"

What you need to know before you call it

  1. It requires a client key. Unauthenticated, it answers 401 with invalid_api_key. Several tools fetch the model list at startup before credentials are configured; that is the usual cause of a mysterious 401 on an otherwise working setup.
  2. Only enabled models appear. A model absent from the list is switched off, not broken. The list reflects the live configuration and can change without warning when the operator edits it — re-fetch periodically rather than caching it for the life of a process.
  3. The ids in it are the only values model accepts — plus each model's aliases, which are not published in the listing. Matching is exact and case-sensitive.
  4. /v1/models/{id} matches the listed id only. An alias that works fine in a chat request returns 404 here. Ids containing a slash (vendor/name) work as written — the path accepts the whole remainder.
  5. The backend's real model name is never in the document, anywhere, at any nesting level. Do not try to infer it; route on the public id.
  6. Prices are decimal strings in USD per single token — not per million, and not JSON numbers. "0.000000003" loses its last digits through a float, so parse it as a decimal if you are reconciling a bill.
  7. A missing pricing object means nobody priced that model, not that it is free. A price that was never set is published as nothing rather than as zero.

OpenAI's envelope on the outside, so an unmodified OpenAI client unwraps it; OpenRouter's model document on the inside, so a client that wants to know what a model costs and accepts can read it without asking anyone.

Reconciling a bill from the listing

The listing is a promise, and it is kept: the usage.usage figure on a response is the published rates multiplied by the token counts on the same response. Cached input is carved out of prompt_tokens and reasoning out of completion_tokens, so nothing is counted twice:

cost = (prompt_tokens - cached_tokens)         * pricing.prompt
     +  cached_tokens                          * pricing.input_cache_read
     + (completion_tokens - reasoning_tokens)  * pricing.completion
     +  reasoning_tokens                       * pricing.internal_reasoning
     +  pricing.request

Use the overrides entry that covers the UTC moment the request ran, if any, and the standing rates otherwise.

/provider/models is a separate document, meant for an aggregator polling this relay as an upstream provider. It is off by default and may require its own token. It is not part of the OpenAI surface — do not point a client at it.

8. Errors

Failures come back in the OpenAI error shape, with the HTTP status matching.

{
  "error": {
    "message": "model \"gpt-9\" is not available on this relay",
    "type": "invalid_request_error",
    "code": "model_not_found"
  }
}
StatuscodeWhen
400—Malformed JSON, a missing or empty model field, or a body this model will not accept.
401invalid_api_keyMissing or unknown client key. Also what an unauthenticated GET /v1/models gets.
403invalid_api_keyThe key is disabled.
403model_forbiddenThe key exists but is not allowed that model.
403forbiddenThe calling IP is blocked.
404model_not_foundUnknown model id — or a known alias asked for at /v1/models/{id}.
404not_foundNo route for that path.
413too_largeThe body is over the size limit, or the prompt is over the model's input ceiling. The message says which.
429rate_limit_exceededA per-minute rate limit or a daily request/token quota is spent. The per-minute refusal carries Retry-After.
499—Recorded, not sent: you disconnected before the answer finished.
502upstream_unavailableThe model could not answer. Retry with backoff; if it persists, tell the operator and quote X-Relay-Request-Id.
503overloadedToo many requests in flight and the queue is full or timed out. Carries Retry-After.
504timeoutThe model took too long to answer.

An upstream failure is reported as this relay's failure, on purpose. The status is mapped by class and the wording is ours: no upstream name, host, model or error text ever reaches a caller. In particular, an upstream rejection of the relay's own credentials comes back as 502, never as 401 — because your key was fine, and telling you otherwise would send you debugging the wrong thing.

Retry policy we recommend

  • 429 and 503: honour Retry-After when present, otherwise exponential backoff from ~1 s.
  • 502 and 504: retry up to two or three times with backoff. The relay already retries transient upstream failures and falls through to fallback backends before it gives up, so a 502 that reaches you has already been tried more than once.
  • 400, 401, 403, 404, 413: do not retry. Fix the request or the credentials.

Output rateper model, per key kindA company key's stream may be paced to a tokens-per-second ceiling. Private keys are never paced.

There is no message-count limit of its own: a conversation is bounded by the model's context length and by the body size above. CORS is configured per relay; preflight is answered on every public path.

Streaming, OpenAI Python SDK

stream = client.chat.completions.create(
    model="Wissangeni-512B-V1",
    messages=[{"role": "user", "content": "Write a haiku."}],
    user="tenant-42:user-9f3c1ab7",
    stream=True,
)

usage = None
for chunk in stream:
    if chunk.usage is not None:       # the final frame: choices is empty here
        usage = chunk.usage
        continue
    if not chunk.choices:             # guard — do not assume choices[0] exists
        continue
    piece = chunk.choices[0].delta.content
    if piece:
        print(piece, end="", flush=True)

print("\n", usage)

Streaming, Node with fetch

const res = await fetch("https://<your-relay-host>/v1/chat/completions", {
  method: "POST",
  headers: {
    "Authorization": "Bearer Kunci-Zeiko-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "Content-Type": "application/json",
    "X-User-Id": "tenant-42:user-9f3c1ab7",
  },
  body: JSON.stringify({
    model: "Wissangeni-512B-V1",
    messages: [{ role: "user", content: "Hello!" }],
    stream: true,
  }),
});

const reader = res.body.getReader();
const decoder = new TextDecoder();
let buf = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buf += decoder.decode(value, { stream: true });

  // Frames are separated by a blank line; tolerate CRLF from proxies.
  let m;
  while ((m = /\r?\n\r?\n/.exec(buf)) !== null) {
    const frame = buf.slice(0, m.index);
    buf = buf.slice(m.index + m[0].length);

    for (const line of frame.split(/\r?\n/)) {
      if (line.startsWith(":")) continue;          // keep-alive comment
      if (!line.startsWith("data:")) continue;
      const data = line.slice(5).trim();
      if (data === "[DONE]") continue;             // terminator, not JSON

      const json = JSON.parse(data);
      if (json.error) { console.error(json.error.message); continue; }
      if (json.usage) { console.log("\ncost:", json.usage.cost); }
      const piece = json.choices?.[0]?.delta?.content;
      if (piece) process.stdout.write(piece);
    }
  }
}

A support question that quotes one can be traced to the exact request row — timing, token counts, the backend that served it and what it cost. A question without one usually cannot.
