2. Authentication

Every endpoint except /health and CORS preflight takes your API key as a bearer token:

Authorization: Bearer Kunci-Zeiko-xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx

Keys are the literal prefix Kunci-Zeiko- followed by a version-4 UUID, so a key is only ever hex digits and hyphens and can be pasted anywhere without being mangled. A key sent bare, with no Bearer scheme in front of it, is also accepted, because some clients send it that way.

Your key is issued to you directly. Keep it server-side: anyone holding it can spend against your account. If you believe it has been exposed, ask us for a replacement and the old one stops working immediately.

The model catalogue needs the key too. GET /v1/models is authenticated. A client that fetches the model list before it has been given credentials gets 401, not an empty list. That is the usual cause of a mysterious 401 on an otherwise working setup.

3. Chat completions

POST /v1/chat/completions takes the ordinary OpenAI request body. Two fields are required: model and messages.

  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user",   "content": "Hello!"}
  ],
  "stream": true,
  "temperature": 0.7,
  "max_tokens": 512,
  "user_id": "tenant-42:user-9f3c1ab7"
}

messagesRequired. The usual role / content array.

Check supported_parameters before relying on a parameter. Each model's catalogue entry lists exactly what it accepts. Sending something not on that list is not an error; it simply has no effect.

Other endpoints

/v1/completions takes the legacy prompt-style body and is billed identically. /v1/embeddings takes model plus input (a string or an array of strings) and returns the standard embeddings response. Neither streams.

4. Identifying your end users

Send one field, user_id, on every request. It is a stable, opaque identifier for the person the request is for.

{
  "model": "Wissangeni-512B-V1",
  "messages": [ ... ],
  "user_id": "tenant-42:user-9f3c1ab7"
}

That is the whole integration. There is nothing else to set, no header to add, and nothing to configure on your side. We take that one value and handle everything downstream of it.

One alternative spelling is worth knowing: user, the field an OpenAI client already sends natively, is read as the same value, so user="tenant-42:user-9f3c1ab7" does the job without extra_body. It wins if both arrive. Pick one spelling and keep to it — sending a different one on a different call is a different partition, and every cache hit is lost.

Why it matters

user_id is the prompt-cache partition key. Two things follow from it, and both are worth money:

  • Isolation. Requests carrying different user_id values can never reuse each other's cached prompt prefix. Without the field, everyone on your API key shares a single partition, so one customer's prefix becomes reusable by another customer's request.
  • Cost and speed. A cached prefix is billed at the cache-read rate, a small fraction of the fresh-input rate, and it removes most of the time-to-first-token on a long system prompt. A user_id that changes between requests throws every cache hit away; a stable one keeps them.

You can see it working: usage.prompt_tokens_details.cached_tokens appears on the response once a prefix is being reused, and is absent while it is not.

Choosing the value

RuleWhy
StableThe same person gets the same string on every request, across sessions and restarts. This is what makes the cache hit.
UniqueTwo different people must never share one value, or they share a cache partition.
OpaqueA hash, a UUID, or an internal account id. Never an email address, phone number, username or real name.
Short and ASCIIUp to 120 characters. Keep well under it.

Omitting user_id is allowed and the request still succeeds. You simply get no isolation and, in practice, far fewer cache hits.

Usage and cost

prompt_tokens counts your own messages only, measured as they arrived. Anything added on your behalf is not charged to you, so the figure matches what you sent.

FieldTypeMeaning
usage.prompt_tokensintegerInput tokens.
usage.completion_tokensintegerOutput tokens, reasoning included.
usage.total_tokensintegerThe two above, added.
usage.prompt_tokens_details.cached_tokensintegerCache-hit portion of the input. Never larger than prompt_tokens. Absent when zero.
usage.completion_tokens_details.reasoning_tokensintegerReasoning portion of the output. Absent when zero.
usage.costnumberWhat this request cost, in USD, to nine decimal places. Also repeated as usage.usage for clients that read that name. One number, never two prices. Both are absent together on a model carrying no published price at all.

Nine decimal places is deliberate: a short request at a tenth of a dollar per million tokens comes to a few millionths of a cent, and rounding to six would report it as free. Parse it as a decimal, not a float, if you are reconciling invoices.

Response headers

HeaderValue
X-Request-IdSame UUIDv4 as id, on streaming and non-streaming answers alike. id in the body is the copy that is always there, so read it from there if you record only one. An error carries neither — a request refused before it reached a model never got an id — so quote the time, the model and the status instead.
Content-Typeapplication/json, or text/event-stream; charset=utf-8 when streaming.
Retry-AfterSeconds to wait. Sent with 429 and 503.

6. Streaming

Send "stream": true and the response is text/event-stream: one data: frame per chunk, then a final frame carrying usage, then [DONE].

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1",
       "choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1",
       "choices":[{"index":0,"delta":{"content":"Hel"},"finish_reason":null}]}

: still working on it

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1",
       "choices":[{"index":0,"delta":{"content":"lo!"},"finish_reason":"stop"}]}

data: {"id":"32dadfde…","object":"chat.completion.chunk","created":1789936200,
       "model":"Wissangeni-512B-V1","choices":[],
       "usage":{"prompt_tokens":18,"completion_tokens":256,"total_tokens":274,
                "cost":0.010293}}

data: [DONE]

(Wrapped for print. On the wire each data: payload is a single line, and every frame ends with a blank line.)

What a client must handle

FrameRule
First frameCarries delta.role: "assistant" and usually no content. Do not assume it has text.
Content framesdelta.content is a string fragment; concatenate in arrival order. A reasoning trace, where a model exposes one, arrives as delta.reasoning_content alongside it.
Tool callsdelta.tool_calls arrives as partial fragments keyed by index: accumulate function.arguments across frames before parsing.
Comment linesA line beginning with : is an SSE comment sent to hold the connection open during a quiet moment. Discard it. Whatever follows the colon is free text and will change; never match on it, and never try to JSON-parse it. A compliant SSE parser already discards these; a hand-rolled one that only reads lines starting data: is also fine.
Final usage frameCarries usage, and it always arrives. Detect it by the presence of usage, not by an empty choices: it usually has choices: [], but the last frame can instead carry both usage and a final choice at once. So a client has to do two things — read usage off whichever frame carries it, and guard choices[0] rather than assume it exists.
Error frameIf a request fails part-way through, a frame carrying {"error":{"message":…,"type":"server_error"}} is sent before [DONE], so a stream that has started never just ends in silence. The HTTP status stays 200, because it was sent before anything went wrong.
data: [DONE]The terminator. Always last, and not JSON.

Practical notes

  • id, created and model are identical on every frame of one response.
  • Each choice carries native_finish_reason beside finish_reason, always the same value. Read either; do not expect them to differ.
  • Frames can split across TCP reads. Buffer until a blank line before parsing, and accept both \n\n and \r\n\r\n as the separator.
  • A multi-byte character is never split across two frames' delta.content.
  • Use curl -N, and turn off response buffering in your HTTP client.
  • Set your client timeout above the maximum request duration in section 9. With keep-alives, an idle-read timeout will not fire spuriously, but a total-request timeout can.
  • Disconnecting mid-stream stops the work. You are charged for what was generated up to that point.

7. The model catalogue

GET /v1/models and GET /models return the identical document. /v1/models/{id} returns a single entry.

curl https://ai.zeiko.biz.id/v1/models \
  -H "Authorization: Bearer Kunci-Zeiko-xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx"

Before you call it

  1. It needs your API key. Unauthenticated it answers 401.
  2. These ids are what model should be set to. Matching is exact and case-sensitive. A name issued to you that is not in the listing still resolves, but the listed id is the one to integrate against.
  3. Re-fetch periodically. The catalogue reflects what is currently offered and can change; do not cache it for the lifetime of a process.
  4. Prices are decimal strings in USD per single token, not JSON numbers, and not per million. "0.000000003" loses its last digits through a float.
  5. A missing pricing object means no published price, not a free model.
  6. These models are sold at three prices, not one. Which one you pay is decided by the reasoning_effort you send, before anything else is read. pricing.bands publishes all three; the top-level rates are the default band, and pricing.default_band names the one a request that sends no reasoning_effort at all lands on.
  7. A field that is absent was never set. An unset description, context_length, max_completion_tokens or default_parameters is left out rather than published as "", 0 or null.

Checking a bill against the catalogue

usage.cost is the published rates multiplied by the token counts on the same response. Cached input is carved out of prompt_tokens and reasoning out of completion_tokens, so nothing is counted twice:

cost = (prompt_tokens - cached_tokens)         * pricing.prompt
     +  cached_tokens                          * pricing.input_cache_read
     + (completion_tokens - reasoning_tokens)  * pricing.completion
     +  reasoning_tokens                       * pricing.internal_reasoning
     +  pricing.request

Start from the band you asked for — pricing.bands[…] for the reasoning_effort you sent, or pricing.bands[pricing.default_band] if you sent none. Then use whichever overrides entry covers the UTC moment the request ran, and the standing rates otherwise.

One answer is not priced by its tokens, and it is the one that would otherwise look wrong. A reply that declines the request — the model saying it will not answer — is charged as a single flat amount instead of the tokens it took to say so. It is an ordinary 200 with ordinary token counts, and usage.cost carries that flat amount, so the formula above will not reproduce it. Reconcile from usage.cost, which is always the amount charged; the formula is how you check an answered request, not a substitute for the figure on the response.

429rate_limit_exceededA per-minute rate limit or a daily quota is spent. The per-minute refusal carries Retry-After.

503overloadedTemporarily at capacity. Carries Retry-After.
504timeoutThe model took too long to answer.

Retry policy

  • 429 and 503: honour Retry-After when present, otherwise exponential backoff from about one second.
  • 502 and 504: retry two or three times with backoff.
  • 400, 401, 403, 404, 413: do not retry. Fix the request or the credentials.
  • 500: retry once, then report it. A second one on the same request is not a blip.

Streaming, OpenAI Python SDK

stream = client.chat.completions.create(
    model="Wissangeni-512B-V1",
    messages=[{"role": "user", "content": "Write a haiku."}],
    extra_body={"user_id": "tenant-42:user-9f3c1ab7"},
    stream=True,
)

usage = None
for chunk in stream:
    if chunk.usage is not None:       # take usage off whichever frame carries it
        usage = chunk.usage           # and keep going: it may carry text too
    if not chunk.choices:             # guard - never assume choices[0] exists
        continue
    piece = chunk.choices[0].delta.content
    if piece:
        print(piece, end="", flush=True)

print("\n", usage)

Streaming, Node with fetch

const res = await fetch("https://ai.zeiko.biz.id/v1/chat/completions", {
  method: "POST",
  headers: {
    "Authorization": "Bearer Kunci-Zeiko-xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    model: "Wissangeni-512B-V1",
    messages: [{ role: "user", content: "Hello!" }],
    user_id: "tenant-42:user-9f3c1ab7",
    stream: true,
  }),
});

const reader = res.body.getReader();
const decoder = new TextDecoder();
let buf = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buf += decoder.decode(value, { stream: true });

  // Frames are separated by a blank line; tolerate CRLF from proxies.
  let m;
  while ((m = /\r?\n\r?\n/.exec(buf)) !== null) {
    const frame = buf.slice(0, m.index);
    buf = buf.slice(m.index + m[0].length);

    for (const line of frame.split(/\r?\n/)) {
      if (line.startsWith(":")) continue;          // keep-alive comment
      if (!line.startsWith("data:")) continue;
      const data = line.slice(5).trim();
      if (data === "[DONE]") continue;             // terminator, not JSON

      const json = JSON.parse(data);
      if (json.error) { console.error(json.error.message); continue; }
      if (json.usage) { console.log("\ncost:", json.usage.cost); }
      const piece = json.choices?.[0]?.delta?.content;
      if (piece) process.stdout.write(piece);
    }
  }
}
